1.2 Purpose of This Document

This Database Design Document defines the complete relational data architecture for the Household Grocery Food Log application (project code: project1), a cloud-hosted web application for a single household where members log grocery shopping trips, track individual food items, mark items as consumed, and audit all activity. [Source: Concept JSON "requirements" section]

The document specifies the design of the following four core database entities implemented in MySQL:

# Entity Table Name Category Description
1 User users Core A household member with role-based access; supports local (email/password) and Google OAuth accounts [Source: Concept Node "user" (dataObjects)]
2 ShoppingTrip shopping_trips Core One grocery shopping session logged by a member [Source: Concept Node "shopping_trip" (dataObjects)]
3 FoodItem food_items Core An individual food item logged during a shopping trip; lifecycle available → consumed [Source: Concept Node "food_item" (dataObjects)]
4 ActivityLog activity_logs System Audit trail of every meaningful action in the app [Source: Concept Node "activity_log" (dataObjects)]

The intended audience includes: database administrators responsible for MySQL schema provisioning, backend developers implementing the Node.js + Express data access layer, QA engineers validating data integrity rules, and project stakeholders approving the design.

2.1.2 Platform Selection Rationale

The following characteristics of the application's data model justify a relational platform and are all directly traceable to the Concept JSON:

#RationaleEvidence in Concept
R-01 Strongly relational data model. The four entities are interconnected via explicit foreign keys: shopping_trips.user_id, food_items.shopping_trip_id, food_items.consumed_by_user_id, and activity_logs.user_id. A relational engine enforces this referential integrity natively. [Source: Concept Nodes "shopping_trip", "food_item", "activity_log" — foreignKey definitions]
R-02 Transactional multi-row writes. The "Create Shopping Trip" operation persists one shopping_trips row plus multiple food_items rows plus one activity_logs row in a single logical unit, requiring ACID transactions. [Source: Diagram "flow_add_shopping" — Node "step_save_trip" and Node "step_log_add_activity"; API Endpoint "ep_create_trip"]
R-03 Uniqueness constraints at the data tier. Business rules require unique username, unique email across all auth providers, and unique google_id — all enforceable via MySQL unique indexes. [Source: Concept Node "user" — indexes; Concept Node "rule_unique_email_providers"]
R-04 Enumerated domain values. Fields such as user.role, user.auth_provider, food_item.unit, food_item.status, and activity_log.action_type are defined as closed enumerations, mapping directly to MySQL ENUM columns or CHECK-constrained columns. [Source: Concept Nodes "user", "food_item", "activity_log" — enum field definitions]
R-05 Aggregation workloads. The dashboard quick stats (total spent this month) and the scheduled Monthly Spend Rollup job aggregate shopping_trip.total_amount and food_item counts — standard SQL SUM/COUNT/GROUP BY operations. [Source: Concept Node "job_monthly_stats"; Concept Node "dashboard" item "dash_stats"; API Endpoint "ep_dashboard_summary"]
R-06 State machine persistence. The Food Item Lifecycle (status: available → consumed) and Member Account Lifecycle (is_active: active ↔ deactivated) persist cleanly as indexed status columns. [Source: Concept Nodes "sm_food_item", "sm_user" (stateMachines)]

INV-04 — Single Consumption: A FoodItem's status may transition from available to consumed exactly once; an update attempting to consume an already-consumed item is rejected. [Source: Concept Node "rule_consumed_excluded"; Concept Node "food_item" — indexes; Environment Node "cfg_flag_show_consumed"]

The User entity represents a household member with role-based access. It supports two authentication providers: local (username/password, hashed with bcrypt) and google (Google OAuth 2.0, with no local password). Every self-registered or Google-created account starts with the member role; only an existing Admin can upgrade an account to admin via the User Management screen. The entity is auditable and uses soft deletion (deactivation via is_active) rather than physical deletion. 4.3 Entity E-03: FoodItem (Table: food_items)

4.3.1 Entity Description

The FoodItem entity represents an individual food item logged during a shopping trip, with a two-state lifecycle: available → consumed. Items are created in batch as children of a ShoppingTrip, always starting with status=available. Consumed items remain in the database permanently for history/audit. The entity is auditable and does not use soft deletion. DELIMITER //
-- =====================================================================
-- Procedure: sp_consume_food_item
-- Purpose: available -> consumed transition with no-double-consume guard.
-- [Source: State Machine "sm_food_item" - transition "t_consume";
--          Business Rule "rule_no_double_consume"]
-- =====================================================================
CREATE PROCEDURE sp_consume_food_item (
    IN p_item_id        CHAR(36),
    IN p_consumer_id    CHAR(36),
    IN p_activity_id    CHAR(36)
)
BEGIN
    DECLARE v_status    ENUM('available','consumed');
    DECLARE v_item_name VARCHAR(150);
    DECLARE v_actor     VARCHAR(201);

    FROM food_items

        consumed_by_user_id = p_consumer_id,
        consumed_at         = CURRENT_TIMESTAMP
    WHERE id = p_item_id;

    -- Step: step_log_consume_activity
    SELECT CONCAT(first_name, ' ', last_name) INTO v_actor
    FROM users WHERE id = p_consumer_id;

    CALL sp_log_activity(
        p_activity_id,
        p_consumer_id,
        'consume_item',
        CONCAT(v_actor, ' marked ', v_item_name, ' as consumed'),
        'food_item',
        p_item_id

    COMMIT;
END//

6.5.3 Food Item Validation & Double-Consumption Triggers

Data-tier enforcement of field validity (name present, quantity > 0, unit set, price ≥ 0) and the single-consumption guarantee of the Food Item Lifecycle (available → consumed, never consumed → consumed again, and no reversal transition is declared). [Source: Business Rules "rule_item_fields_valid", "rule_no_double_consume"; State Machine "sm_food_item"] 

DELIMITER //
-- =====================================================================
-- Trigger: trg_food_items_validate_ins
-- [Source: Business Rule "rule_item_fields_valid" - condition:
--  name.length > 0 && quantity > 0 && unit != null && price >= 0]
-- =====================================================================
CREATE TRIGGER trg_food_items_validate_ins
BEFORE INSERT ON food_items
FOR EACH ROW
BEGIN
    IF CHAR_LENGTH(TRIM(NEW.name)) = 0
       OR NEW.quantity <= 0
       OR NEW.unit IS NULL
       OR NEW.price < 0 THEN
        -- messageKey: error.food_item.invalid_fields
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Each item needs a name, a positive quantity, a unit, and a non-negative price.';
    END IF;
END//

-- =====================================================================
-- Trigger: trg_food_items_validate_upd
-- Same field validation on update (Admin edit path, ep_edit_item).
-- [Source: Business Rule "rule_item_fields_valid";
--          API Endpoint "ep_edit_item"]
-- =====================================================================
CREATE TRIGGER trg_food_items_validate_upd
BEFORE UPDATE ON food_items
FOR EACH ROW
BEGIN
    IF CHAR_LENGTH(TRIM(NEW.name)) = 0
       OR NEW.quantity <= 0
       OR NEW.unit IS NULL
       OR NEW.price < 0 THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Each item needs a name, a positive quantity, a unit, and a non-negative price.';
    END IF;

    -- =================================================================
    -- No double consumption: once consumed, status may not change again
    -- and may not be consumed twice.
    -- [Source: Business Rule "rule_no_double_consume";
    --          State Machine "sm_food_item" - only transition t_consume]
    -- =================================================================
    IF OLD.status = 'consumed' AND NEW.status = 'consumed'
       AND (NEW.consumed_by_user_id <> OLD.consumed_by_user_id
            OR NEW.consumed_at <> OLD.consumed_at) THEN
        -- messageKey: error.food_item.already_consumed
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'This item has already been marked as consumed.';
    END IF;

    -- Consumption metadata must accompany the consumed state
    IF NEW.status = 'consumed'
       AND (NEW.consumed_by_user_id IS NULL OR NEW.consumed_at IS NULL) THEN
        SIGNAL SQLSTATE '45000'
            SET MESSAGE_TEXT = 'Consumed items must record consumed_by and consumed_at.';
    END IF;
END//

6.6 Scheduled Event: Monthly Spend Rollup (Phase 3)

The Concept JSON defines a scheduled job — job_monthly_stats, cron 0 2 1 * * — that precomputes last month's total spend and item counts on the 1st of each month at 02:00 for fast Dashboard stats. The implementation below uses a rollup table plus a MySQL scheduled EVENT. The equivalent schedule may alternatively be driven from the Node.js layer (e.g., a cron-triggered Express job calling the same procedure); the choice is deployment-specific and is to be defined during detailed design phase. [Source: Event/Job "job_monthly_stats"; Phase "phase_3"] 

-- =====================================================================
-- Rollup table for precomputed monthly stats (Phase 3)
-- [Source: Event/Job "job_monthly_stats" - "precompute last month's
--          total spend and item counts for fast dashboard stats"]
-- =====================================================================
CREATE TABLE IF NOT EXISTS monthly_stats (
    month_start DATE          NOT NULL,
    trip_count  INT           NOT NULL DEFAULT 0,
    total_spent DECIMAL(10,2) NOT NULL DEFAULT 0.00,
    item_count  INT           NOT NULL DEFAULT 0,
    computed_at DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (month_start)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

DELIMITER //
CREATE PROCEDURE sp_rollup_monthly_stats()
BEGIN
    DECLARE v_month DATE;
    SET v_month = DATE_FORMAT(DATE_SUB(CURDATE(), INTERVAL 1 MONTH), '%Y-%m-01');

    INSERT INTO monthly_stats (month_start, trip_count, total_spent, item_count, computed_at)
    SELECT month_start, trip_count, total_spent, item_count, CURRENT_TIMESTAMP
    FROM vw_monthly_spend
    WHERE month_start = v_month
    ON DUPLICATE KEY UPDATE
        trip_count  = VALUES(trip_count),
        total_spent = VALUES(total_spent),
        item_count  = VALUES(item_count),
        computed_at = CURRENT_TIMESTAMP;
END//
DELIMITER ;

-- =====================================================================
-- Event: evt_monthly_spend_rollup
-- Schedule equivalent to cron "0 2 1 * *" — 02:00 on the 1st of month.

-- [Source: Event/Job "job_monthly_stats" - trigger "cron: 0 2 1 * *"]

ON SCHEDULE EVERY 1 MONTH
STARTS (TIMESTAMP(DATE_FORMAT(DATE_ADD(CURDATE(), INTERVAL 1 MONTH), '%Y-%m-01')) + INTERVAL 2 HOUR)

7.3 Sensitive Data Protection

7.3.1 Password Storage

SEC-BR-01 — Passwords Always Hashed: Local-account passwords MUST be stored as bcrypt hashes in users.password_hash and never in plain text. The field is flagged sensitive: true and excludeFromApi: true — it is never serialized into API responses. The bcrypt cost factor is configurable via BCRYPT_SALT_ROUNDS (example: 12). The database-side function fn_is_bcrypt_hash (Section 6) provides defense-in-depth validation. [Source: Business Rule "rule_password_hashed"; Data Object "user" — field "password_hash"; Environment "cfg_bcrypt_rounds"]
SEC-BR-02 — Google Accounts Have No Local Password: Accounts with auth_provider = 'google' MUST have password_hash = NULL. Enforced at the application layer and by trigger trg_users_google_no_password (Section 6). Violation message: "Google-authenticated accounts cannot have a local password." (error.user.google_no_password). [Source: Business Rule "rule_google_no_password"]
SEC-BR-03 — Unique Email Across Providers: The UNIQUE index on users.email guarantees an email can only belong to one account, whether local or Google. Violation message: "This email is already registered to an account." (error.user.email_taken). [Source: Business Rule "rule_unique_email_providers"; Data Object "user" — unique index on "email"]
